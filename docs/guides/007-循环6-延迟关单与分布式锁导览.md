# 导览 007：循环 6 —— 延迟关单、库存回补与分布式锁

> 讲法同前：比喻搭脚手架，紧跟规范表述。

## 这一循环做了什么

抢到却不付款的"僵尸订单"现在会被自动收割：**20 分钟不付款 → 订单自动关闭 →
库存回到货架（别人能再抢）→ 限购释放（自己也能再抢）**。这由两套互为备份的机制驱动：
延迟消息（主力）＋扫表兜底（保险）；多实例部署时靠 Redis 分布式锁保证兜底扫描不重不漏。

## 一个真实的工程决策：15 分钟为什么变成了 20 分钟

PRD 原定 15 分钟关单。实现时发现：**开源版 RocketMQ 的延迟消息只支持 18 个固定档位**
（1s 5s 10s 30s 1m…9m 10m 20m 30m 1h 2h），没有 15 分钟这一档；任意时间的定时消息
是 RocketMQ 5.x 商用特性的地盘。两个选择：为 15 分钟引入重量级方案，或取最接近的
20 分钟档。我们选后者——**业务时间让一步，换来架构轻一步**，PRD 已同步修订。
面试讲这种"标准组件能力边界 → 业务参数调整"的取舍，比硬凑更加分。

## 三层防线：一条订单从创建到被收割

```
建单成功（消费者事务内）
  └─ 埋雷：发一条 ORDER_CLOSE_DELAY 延迟消息，级别15（20分钟后才投递）
        ↓ 20分钟后到点
延迟消息消费者 → OrderCloseService.closeIfUnpaid
        ↓ 万一消息丢了/消费者当时挂了
扫表兜底任务（每60秒）：查超时未付订单 → 同一个 closeIfUnpaid
```

两套机制**竞速但不冲突**：谁先到谁生效，后到的被状态机守卫挡下（空转返回）。

## 关单动作的正确顺序（本循环最重要的细节）

```
markClosedIfCreated：UPDATE ... SET status=3, active_flag=NULL WHERE order_no=? AND status=0
  ├─ 影响 0 行（已付款/已关过）→ 直接返回，什么都不做
  └─ 影响 1 行 → 才执行：Redis 库存+1、删判重标记、写库存流水
```

**必须先动状态机、后回补库存**。反过来（先回补再关单）在并发重复关单时会把同一份
库存补两次。测试 `double_close_refunds_stock_only_once` 验证的正是这一点：
连关两次，库存只 +1。这个"守卫在先、资源变更在后"的原则和支付回调里的状态机是
同一个思想——全项目第三处复用。

三个动作的意义：status=3（账面上关闭）；active_flag=NULL（唯一索引不再约束，
**限购释放**——这就是循环 3 讲的 NULL 技巧的后半段）；库存+1（回到货架）。

## 分布式锁（场景11）：扫表任务为什么需要它

问题：将来如果主程序部署两个实例（8080/8081），每 60 秒**两台机器都会醒来扫表**——
没有锁就各扫各的（浪费＋日志混乱；有副作用的话就是事故）。

方案：Redis 分布式锁，两个动作：

- **加锁**：`SET lock:order-close 令牌 NX EX 30`——NX = 没人持有才能成功（互斥）；
  EX = 30 秒自动过期（持有者崩溃也不会死锁）；令牌 = 本实例启动时的随机 UUID；
- **解锁**：Lua 脚本"GET 出来的值等于自己的令牌才 DEL"——防止 A 的锁恰好过期、
  B 拿到锁之后，A 干完活回来把 **B 的锁**删了（令牌校验保证只能删自己的）。

每轮扫描：抢到锁的干活，没抢到的直接跳过（日志会打"本轮由其他实例执行"）。

## 配置驱动（验收用的机关）

```yaml
order:
  close-delay-level: ${ORDER_CLOSE_DELAY_LEVEL:15}   # 15=20分钟；3=10秒
  close-minutes: ${ORDER_CLOSE_MINUTES:20}           # 扫表的超时线
  close-scan-seconds: ${ORDER_CLOSE_SCAN_SECONDS:60} # 扫表间隔
```

冒号后是**环境变量占位符**：默认 15（20 分钟），验收时在 IDEA 运行配置里注入
`ORDER_CLOSE_DELAY_LEVEL=3` 即变 10 秒——不改代码就能加速验证。

## 亲眼看（bash docs/scripts/verify_loop6.sh）

脚本会**自己起第二个实例（8081）**演示分布式锁，然后：
抢购不付款 → 等 15 秒（延迟级别 3=10 秒）→ 订单变 status=3、库存回升、
**同一玩家对同一商品再次抢购成功**（active_flag=NULL 释放限购的活体证明）。
对照窗口：DBeaver 看 order_info 的 active_flag 列从 1 变 NULL；
两个实例的控制台日志——一个在扫表，另一个打"本轮由其他实例执行，跳过"。
