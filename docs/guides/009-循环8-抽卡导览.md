# 导览 009：循环 8 —— 抽卡（概率、硬保底与不可篡改的账本）

> 讲法同前：比喻搭脚手架，紧跟规范表述。

## 这一循环做了什么

抽卡玩法上线：单抽/十连（同一接口带次数参数）、三档稀有度按权重出卡、
**90 抽硬保底**、概率对外公示、每一抽进只增不改的流水。简历第 6 条
（"按丢失容忍度选存储"）在这一循环落地成代码。

## 三个关键设计

### 1. 存储选型：保底计数为什么不进 Redis（全项目最值钱的方法论）

选存储前先问一句话：**这个数据丢了，后果是什么？**
- 保底计数丢一次 = 玩家抽了 89 次你给他清零 = 舆情上热搜 → 丢失容忍度 **0** → 落 MySQL（user_pity 表，每笔落盘）；
- 排行榜丢一秒玩家无感 → 容忍秒级误差 → 落 Redis。
同一类"计数"数据，因丢失容忍度不同走向不同存储——这就是场景 12 的方法论。

### 2. 硬保底 90 的实现：计数器 + 出金清零

每抽计数 +1；**自然出金（1% 权重）或强制出金（计数到 90）都清零**；
第 90 抽若按权重没出金，直接把结果改写成金色物品并标记 `is_pity_hit`。
正确性铁律：**任何一抽之后的计数必须 ≤ 90**——千抽审计测试用聚合查询验证它。

### 3. 并发正确性：保底计数行上的锁

同一玩家并发抽卡（双端连点）会在 `SELECT ... FOR UPDATE` 的行锁上排队——
后到的抽卡读到的一定是前者提交后的计数，保底绝不跳变、绝不双发。
不同玩家的行互不相同，互不阻塞。这是"用数据库行锁保护临界计数"的标准姿势。

## 一次十连的事务边界（场景 12 的"四动作一次完成"）

```
BEGIN
  1. 条件扣钻 1000（diamond >= 1000 守卫，不足即回滚）
  2. 行锁读保底计数 → 逐抽出卡（加权随机/强制金）→ 每抽写流水
  3. 背包 UPSERT 入包
  4. 钱包流水记 GACHA -1000 → 更新保底计数
COMMIT（任一步失败全回滚：绝不"扣了钻没出卡"）
```

## 概率公示

GET /api/gacha/pool 返回每件物品的 weight 与换算后的概率（89%/10%/1%）
＋当前保底进度。**公示和实现读同一张表**——不存在"页面一套、后台一套"。

## 亲眼看（bash docs/scripts/verify_loop8.sh，约2分钟）

脚本自动充 9000 钻 → 十连看结构 → 连抽满 90 发 → 聚合审计：
**gold_count ≥ 1（90 发内必有金）、max_pity ≤ 90（铁律）**、钱包流水出现 GACHA。
对照窗口：DBeaver 看 gacha_record（只增不改的原始账本）、user_pity（当前计数）。

## 本循环踩到的小坑

新建 gacha_record 表时漏写 PRIMARY KEY（AUTO_INCREMENT 必须挂在键上，
MySQL 直接拒绝建表——报错很直白：there can be only one auto column and it must be defined as a key）。
另：千抽审计最初误用带 LIMIT 50 的展示接口当数据源（断言 1000 条自然失败）——
**展示接口和审计查询必须分开**，展示有分页上限，审计要聚合。
