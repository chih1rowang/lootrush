# 导览 005：循环 4 —— 假支付公司与幂等（回调验签、重复通知、状态机）

> 讲法同前：比喻搭脚手架，紧跟规范表述。本循环是简历第 4 条（幂等）的落地现场。

## 这一循环做了什么

出现了第二个进程：**mock-payment（假支付公司，端口 18090）**。它独立运行，
和主系统（8080）之间只共享三样东西：回调地址、HMAC 密钥、签名规范——
这正是现实里"商户系统"与"支付宝"的关系。玩家现在可以：充值（买钻石）、
为抢购订单付款；而支付公司会"作恶"（延迟回调、重发通知），
我们的系统必须把它们全部正确挡住。

## 四个关键角色

### 1. HMAC 验签：怎么证明"这通电话真是支付宝打来的"

比喻：你和支付公司事先约定一个暗号本；每次通知里附一句用暗号本加密的口令，
接电话的人当场验证口令对不对。
规范表述：**HMAC-SHA256**。双方共享密钥（secret），签名内容为
`orderNo|amount|notifyNo` 拼接后做 HMAC 运算的十六进制串。
收到回调先验签：密钥不在网络上传输，伪造者既不知道密钥也无法构造合法签名。
验签失败 → 401 拒绝并记入通知日志（BAD_SIGN）。

### 2. 幂等三件套：重复通知为什么只处理一次

现实约束：支付公司的"已付款"通知**官方就允许重发**（网络超时对方会重试）。
处理两次 = 发两次道具 = 真金白银事故。三道防线：

| 防线 | 机制 | 拦哪种重复 |
|---|---|---|
| ① 唯一通知号 | pay_notify_log.notify_no 唯一索引，插不进=来过 | 同一条通知重发 N 次（REPEAT 模式） |
| ② 状态机守卫 | `UPDATE ... SET status=1 WHERE status=0`，影响 0 行=已处理过 | 不同通知号但同一订单已付（重复回调） |
| ③ 钱包事务 | 扣款与状态变更同事务，余额不足整体回滚 | 防止"扣了钱订单没付"或反向 |

关键细节：被拦下的重复回调**也要返回成功**（code 0）——支付公司只认"成功"才停止重试；
返回失败会让它永远重试下去。幂等接口的响应语义：**结果幂等，应答友好**。

### 3. 钱包流水（wallet_flow，只增不改）

钻石每一次增减（RECHARGE/PURCHASE，以后还有 GACHA）都写一行流水，带变动后余额。
表只允许 INSERT 不允许 UPDATE/DELETE——这是循环 7 对账能成立的地基：
流水就是"事实"，任何对不上的账都以流水+订单为准。

### 4. 作恶开关（Evil Switch）

假支付公司的灵魂：`POST /mock-pay/switch?mode=...` 切换三种行为——

- **NORMAL**：确认付款后立刻回调一次（正常世界）；
- **DELAY**：30 秒后才回调（模拟网络延迟；循环 6 的延迟关单会用到这个观察）；
- **REPEAT**：同一条通知（相同 notifyNo+签名）在 6 秒内到达 3 次——**幂等的实测现场**。

## 充值与购买统一走支付

充值 = 创建一张 RECHARGE 订单（goods_id=0、active_flag=NULL 不占限购名额）→
跳假支付页付款 → 回调加钻石；购买 = PURCHASE 订单 → 同一个支付页 → 回调扣钻石。
**两类订单共用一条回调链路**——一条链路两层故事，维护和讲解都只此一份。

## 怎么跑假支付公司

方式一（推荐）：IDEA 里 File → Open 再打开 `mock-payment` 文件夹（新窗口），
等依赖下载完点运行——两个窗口各跑一个进程。
方式二：Git Bash 里 `./mvnw -q -f mock-payment/pom.xml spring-boot:run`（后台跑）。

## 亲眼看（bash docs/scripts/verify_loop4.sh）

脚本自动完成：上架→抢购→NORMAL 付款→查余额恰好减一次→第二件商品 REPEAT 模式
付款（同通知三连发）→ **余额仍然只减一次** → 订单流水可见两笔 PROCESSED。
假支付页（浏览器版）：http://localhost:18090/pay.html?orderNo=xxx&amount=xx
（orderNo 从抢购响应或"我的订单"里拿）。

对照窗口：
- **DBeaver**：pay_notify_log 表——REPEAT 模式后可见 3 行相同 notify_no 吗？不，
  只有 1 行（唯一索引把后两条挡在了门外），result=PROCESSED；wallet_flow 表每笔钻石变动一行；
- **Zipkin**：回调请求的行程单；REPEAT 时能看到 3 条同形请求，后两条极短（唯一索引快速拒绝）。

## 本循环踩到的小坑

PaymentService 引用了还没写的 `OrderMapper.markPaidIfCreated`——"先写调用方后写被调方"
导致编译失败。教训：新增跨文件方法时，先补被依赖的那一层（Mapper），再写调用方；
或写完调用方立刻通编译，把"找不到符号"扼杀在第一时间。
