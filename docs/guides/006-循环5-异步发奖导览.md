# 导览 006：循环 5 —— 异步发奖（付了钱道具必到账）

> 讲法同前：比喻搭脚手架，紧跟规范表述。

## 这一循环做了什么

补上支付后的最后一环：付款成功的购买订单，**道具自动进背包**，订单状态从"已支付"
流转到"已发货"。整条链路异步进行——支付回调不等发货完成就返回（发货慢不能拖死支付），
由消息队列的消费者完成入包。

## 关键设计一：发货消息必须在事务提交后才发（本循环最值钱的考点）

问题：回调处理在一个数据库事务里。如果**事务内**就把发货消息发出去：
消息发完 → 事务却因故回滚 → 消费者为一笔"没付成功"的订单发了货 → 资损事故。

方案：**注册 afterCommit 回调**——事务成功提交的那一刻才真正发送消息。
发送若失败（网络抖动），支付已安全落地不回滚，发货缺口由循环 7 的对账兜底。

规范表述：这是**事务性发件箱（Transactional Outbox）思想的朴素实现**。
面试被问"消息怎么保证在数据落库后才发""发消息和本地事务的一致性怎么处理"，
讲这个 afterCommit + 对账兜底的组合即可；再往上聊才是真正的 Outbox 表方案。

## 关键设计二：发货消费者的幂等两道防线

消息可能被消息队列重投（和支付通知重发同理），道具绝不能发两次：

| 防线 | 机制 |
|---|---|
| ① deliver_flow.order_no 唯一索引 | 同一单的第二条消息插不进 → 直接忽略（幂等锚点） |
| ② 状态机 1→2 条件更新 | `UPDATE ... SET status=2 WHERE status=1`，0 行=已处理过 |

消费者的三个动作包在一个事务里：**记发货流水 → 背包入道具 → 订单标已发货**，
要么全成要么全回滚（对应"发奖三动作做一半崩了"的场景 9）。

## 背包的 UPSERT

入包用数据库原生的 `INSERT ... ON DUPLICATE KEY UPDATE count = count + ?`：
没有这行就插入、有就数量累加——**一条 SQL 原子完成**，不需要"先查有没有再插或改"
（那种两步写在并发下会插入重复行）。

## 一次付款到道具入包的完整旅程

```
支付回调(事务): 状态0→1 → 扣钻石 → 记钱包流水 → [注册afterCommit] → 提交
                                                              ↓ 提交成功才发
                                       DELIVER_GOODS消息 → RocketMQ
                                                              ↓ 异步
              消费者(事务): deliver_flow插行(唯一锚点) → 背包UPSERT → 状态1→2
```

脚本流程：充值保证余额 → 上架并等开售 → 抢购 → 付款 → 等 5 秒 →
**背包出现道具 count=1、订单 status=2、发货流水恰好 1 行**。

## 本循环踩到的两个坑（第二个很值钱）

**坑1（老朋友）：SQL 下划线/驼峰又漏一列。** BagMapper 把 `i.image_url` 写成
`i.imageUrl`——循环 2 同款错误第二次出现。已形成肌肉记忆级检查项：
**每写一个 SELECT，逐列对照表结构**。

**坑2（值钱）：测试没有 @Transactional，被自己昨天的数据毒倒了。**
PayCallbackTest 上一版没加事务注解，昨天首跑的数据（通知号 N1/SAME...）永久留在库里；
今天第二跑插入同样的通知号撞唯一索引 → 全部走"重复忽略"捷径 → 表面 code=0 实际什么
都没处理 → 断言集体失败。修复：加 @Transactional（每测试自动回滚）+ 物理清除残留行。
教训：**集成测试要么回滚、要么用带时间戳的唯一数据；"昨天是绿的"不代表今天还能绿——
数据库是有记忆的。**（这条已具备写进事故报告的资格，编号 006。）
