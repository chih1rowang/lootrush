## 第〇章 总原则：这个项目是怎么做技术决定的

全项目所有选型只用了三条思考规则，先记住规则，再看每个技术怎么套规则：

**规则一：先问业务压力有多大，再选工具。**
不是"Redis 很火所以用"，而是"几十万人同一秒抢 5000 份货，数据库扛不住，所以需要一个
挡在数据库前面的东西"——那个东西恰好叫 Redis。压力不同，选的工具就不同。

**规则二：先问数据丢了疼不疼（丢失容忍度），再决定放哪。**
"玩家抽了 89 次卡，服务器一重启计数清零"——疼到上热搜，所以保底计数必须放在
**绝不会丢**的地方（MySQL，每笔都刻在硬盘上）。"排行榜晚更新一秒没人发现"——
不疼，所以可以放在**快但可能丢最近几秒**的地方（Redis，放在内存里）。
同一类"计数"，因为"丢了疼不疼"不同，走向了完全不同的存储。

**规则三：每个工具必须能回答"不用它会出什么事故"。**
答不出来的工具就不配进项目（我们因此拒绝了限流中间件、微服务全家桶、K8s 等）。
这份手册里每个技术后面都会附上"不用它会怎样"。

## 第一章 地基四件套：Java、Spring Boot、MyBatis、MySQL

### 1.1 Java：编程语言

**是什么**：你写代码用的语言。所有业务逻辑（扣库存、算保底、对账）都用它写成。
**为什么是它**：国内后端岗位的主流语言，招聘需求最大；我们的目标就是 Java 后端实习。
**面试相关**：我们用的是 Java 17（一个"长期支持版"，即官方承诺维护很多年的稳定版本），
代码里用了它的两个新语法：record（一行定义"只装数据的盒子"）和 switch 新写法。

### 1.2 Spring Boot：零件自动组装厂

**是什么**：一个框架。框架可以理解为"别人搭好的毛坯房"——造一个能接收网络请求的
程序，本来要自己写几百行"接电话、解析来电内容、按内容分派给谁处理、把结果写回去"
的重复劳动，Spring Boot 说"这些我都包了，你只管写业务"。

**它具体干了什么**：
- 你在方法上写一个 `@GetMapping("/ping")`，浏览器访问这个网址就能执行这个方法——
  网络通信那一大坨复杂度被它吃掉了；
- 你声明"我需要一个数据库连接、一个 Redis 连接"，它自动创建好并塞给你
  （这套机制叫"依赖注入"，人话：你列采购单，仓库自动送货上门）；
- 我们还用它的"自动装配"：把某个零件的包放进项目，它就自动配置好——
  但这也是双刃剑，出问题时它"静默不干活"很难查（事故 004 就是这么来的）。

**为什么不用别的**：Java 后端的事实标准，招聘 JD 全在要求它。我们用的版本是
**4.0.9（最新一代）**——全网的教程大多还停在上一代（3.x），所以我们踩了很多
"教程失配"的坑（Jackson 库搬家、插件不再自动装配），这些坑本身就是独家面试素材。

### 1.3 MyBatis：Java 对象和数据库行之间的翻译官

**是什么**：程序内存里的数据是"对象"（一组带名字的值，如用户对象=名字+密码+钻石数），
数据库里的数据是"一行行的表格"。两者形状不同，需要翻译。MyBatis 就是翻译官：
你写 SQL（对数据库下的指令），它负责把参数装进去、把查回的表格组装成对象还给你。

**对比其他选型**：
- **裸写 JDBC**（Java 自带的数据库操作）：每次查库要手动开连接、拼语句、逐列读值、
  关连接——重复劳动极多。MyBatis 把这些全包了。
- **JPA/Hibernate**（另一种框架）：连 SQL 都帮你自动生成，你操作对象它自动改库。
  看似更省事，但生成的 SQL 是黑盒，性能排查困难，复杂查询写起来别扭。
- **我们选 MyBatis**：SQL 自己写、自己掌控（面试常问"SQL 优化"，你得能看见 SQL），
  学习成本适中，国内主流。

**本项目特色用法**：SQL 直接以注解形式写在方法上（小项目清晰直观）；
打开了"下划线转驼峰"自动翻译（数据库列名 `user_id` ↔ Java 字段 `userId`——
两次事故 002/008 都跟这个翻译有关，见事故报告）。

### 1.4 MySQL：唯一可信的"事实源"

**是什么**：关系数据库——把数据存成一张张表（像 Excel），存在硬盘上。
**核心特性**：①每笔写入都落盘（断电不丢）；②支持事务（一组操作要么全成功要么全
撤销）；③支持唯一索引（给某列立"不许重复"的规矩）。

**它在项目里的定位**：**事实源（source of truth）**——所有真正重要的账（用户、订单、
钱包流水、库存流水、抽卡记录）都以 MySQL 为准。Redis、消息队列里的数据都算
"派生数据"，丢了可以从 MySQL 重建。这个定位是对账系统能成立的前提。

**本项目用到的三个 MySQL 深水区**：
- **事务**：`@Transactional` 标注的方法里所有数据库操作要么全成要么全回滚
  （抽卡四动作、发奖三动作都靠它）；
- **唯一索引的 NULL 技巧**：唯一索引不管 NULL 值——我们用它实现"同一人同一商品
  活跃期只能有一单、关单后自动放行再抢"（一条索引干两个活）；
- **隔离级别**：多个事务同时读写时互相能看到什么。默认级别下，一个事务只能看到
  它开始时的快照——这个特性曾让测试"看不见"消费者后写入的数据（事故 008）。

## 第二章 登录与安全：BCrypt、JWT、HMAC、AES、脱敏

### 2.1 BCrypt：密码的搅碎机（单向）

**是什么**：密码加密存储的算法。特点：①每次加密撒随机"盐"（同一密码每次结果不同）；
②故意很慢（暴力破解者也跟着慢）；③**不可逆**（无法从乱码还原密码）。
登录验证时把你输入的密码**再搅一遍**，比对两团乱码是否一致。

**为什么不用 MD5**：MD5 太快 + 同一密码结果永远相同 → 坏人用预先算好的
"常用密码对照表"秒破。**为什么身份证明文不行、密码哈希就行**——见 2.4 的对比。

### 2.2 JWT：电子手环（无状态通行证）

**是什么**：登录成功后发给你的一串字符，分三段：算法.内容.防伪签名。
服务器**不保存**任何手环记录，收到手环时用只有自己知道的密钥验签——
所以叫"无状态"（不需要记账本）。

**对比 Session 方案**：

| | JWT（我们用的） | Session（传统方案） |
|---|---|---|
| 服务器存不存记录 | 不存（省存储、天然支持多台机器） | 存（要一个集中存储或粘住一台机器） |
| 能否提前作废 | 不能，只能等过期 | 能（删掉记录即可） |
| 适合 | 我们这种"令牌短命+可接受"的场景 | 需要强踢人下线的场景 |

**我们的取舍**：手环 12 小时过期；"退出登录"只是前端删手环，服务端无法强制作废
——这是 JWT 的固有代价，面试必问，你能讲清"为什么接受这个代价"。

### 2.3 HMAC：支付公司的敲门暗号

**是什么**：一种"带共享密钥的签名"。支付公司和商户事先共享一个密钥（只有双方知道），
支付公司每次通知都附带"用密钥对通知内容算出的签名"，商户收到后用同一密钥重算比对
——对得上，证明"这通电话真是支付宝打来的，且内容没被篡改"。

**用在哪**：支付回调接口（全项目信任级别最低的门）。**不用它会怎样**：任何人都能
伪造"我付款成功了"的通知白拿道具——真金白银的事故。

### 2.4 AES-GCM：身份证的保险箱（可逆加密）＋ 和 BCrypt 的本质区别

**是什么**：AES 是对称加密（加密解密用同一把钥匙），GCM 是它的一个工作模式
（随机数前缀让同一明文每次密文不同＋自带防篡改校验）。**可逆**——拿着钥匙能还原。

**和 BCrypt 的本质区别（面试高频对比）**：
- **密码用 BCrypt（单向哈希）**：因为密码**永远不需要读回来**——你忘密码是"重设"
  不是"找回"，系统只需验证"你输的和存的是否一致"；
- **身份证用 AES（可逆加密）**：因为实名信息**需要读回来**（防沉迷要判断年龄、
  个人中心要展示）——所以必须可逆，且必须加密存储（合规要求）。
- 一句话总结：**可不可逆，由"要不要读回来"这个业务问题决定**。

**配套细节**：`enc:v1:` 前缀（识别自家密文，防重复加密/解密，未来可升级 v2）；
出参**脱敏**（310\*\*\*\*\*\*1234，接口永远不返回完整证号）。

### 2.5 身份证校验位：合规的小碎件

18 位身份证最后一位是"校验码"（前 17 位加权求和算出来的）。我们实现了完整校验
算法——被拒的不只是格式错的，还有"数字对但校验码错"的假证号。

## 第三章 Redis 的五种用法（重头戏一）

### 3.0 Redis 是什么

**一个把数据放在内存里的小仓库**。内存读取比硬盘快百倍以上，所以它极快；
代价是"相对易失"（默认配置下崩溃可能丢最近几秒的数据）。它**不替代** MySQL，
而是站在 MySQL 前面干"要快、能容忍秒级误差"的活。规则二（丢失容忍度）就是
在 MySQL 和 Redis 之间做选择的核心依据。

### 3.1 用法一：缓存（读多写少的救命稻草）

**场景痛点**：开售前一小时几十万人反复刷同一页货架。每次都去 MySQL 翻，
MySQL 门口挤爆，真正要买的人反而进不来。
**做法**：货架内容抄一份放在 Redis（键 goods:list），大家读 Redis；
Redis 没有 → 查 MySQL → 回写 Redis。这个模式叫 **Cache-Aside（旁路缓存）**。
**三连防**：过期时间随机（防"同一秒集体失效"=雪崩）、空结果也缓存 60 秒
（防恶意刷不存在的数据=穿透）、热点数据提前预热。
**改价的坑**：改价后必须让缓存作废，但"删缓存→改库"的间隙里可能有人读到旧库值
又写回缓存——所以**擦两次黑板**（延迟双删：先删、改库、隔半秒再删一次）。
**不用它会怎样**：数据库在开售前就被读流量打死，抢购根本开始不了。

### 3.2 用法二：Lua 原子扣减（抢购的心脏）

**场景痛点**：库存 1 份，两个人同时买。如果"查库存"和"扣库存"是两步，
两人都查到"还剩 1"然后都扣——**超卖**（卖出 2 份）。
**做法**：写一段 Lua 脚本（小指令集）提交给 Redis，脚本里一口气完成
"看他买过没→查库存→扣库存→标记他买过"。**Redis 是单线程执行**，脚本执行期间
没有任何其他指令能插进来——原子性由此而来。
**不用它会怎样**：超卖=直接赔钱+全员补偿。我们的并发测试：30 线程抢 10 件，
成功恰好 10、终态库存 0（机器验证）。
**配套**：98% 注定失败的人在这层就被拒绝（"已售罄/已抢过"），数据库毫发无伤。

### 3.3 用法三：分布式锁（多台机器的排队取号机）

**场景痛点**：将来部署两个程序实例时，每 60 秒的扫表任务两台机器都会醒来执行——
重复劳动甚至重复副作用。
**做法**：干活的先在 Redis 抢一把锁（SET NX EX：没人持有才能成功+自动过期防死锁），
抢到的干活，没抢到的跳过；干完用 Lua 脚本"核对令牌后删除"（防止 A 的锁过期后
误删 B 的锁）。
**不用它会怎样**：双实例重复扫单；单实例时无感，一扩容就爆雷。

### 3.4 用法四：ZSET 排行榜（跳表的舞台）

**是什么**：ZSET（有序集合）= 每个成员带一个分数、自动按分数排好序的集合。
**场景痛点**：30 万玩家的消费榜，每次刷新要"前 100 名"+"我的排名"。MySQL 方案=
每次全表排序（30 万行），秒崩；ZSET 方案=更新、查前 100、查排名全部是对数级操作。
**实测**：30 万成员下，查前 100 = 4.6 毫秒，查我的排名 = 4.7 毫秒。
**底层是跳表**：多层"快车道"逐层逼近（面试必问"为什么不用红黑树"——范围查询的
实现便利性是关键差异）。
**边界（诚实）**：深翻页（查第 29 万名之后）会慢——但业务只需要前 100 和我的排名，
不越界。

### 3.5 用法五：pipeline 批量管道

**是什么**：把几千条命令打包在一次网络往返里发给 Redis。
**用在哪**：灌 30 万测试玩家——逐条发=30 万次网络往返（灾难）；pipeline 批量
=87 秒干完。

### 3.6 Redis 的选型对比

| 对比项 | Redis（我们用的） | Memcached（另一款内存缓存） | 本地缓存（缓存在程序自己肚子里） |
|---|---|---|---|
| 数据结构 | 丰富（字符串/集合/有序集合等） | 只有简单键值 | 就是程序里的 Map |
| 多机共享 | 支持（独立服务） | 支持 | 不支持（每台机器各一份，会不一致） |
| 功能 | 缓存/锁/排行榜/原子操作 | 只适合纯缓存 | 小打小闹 |
| 结论 | 一个服务覆盖项目五种需求 | 功能不够 | 双实例部署下直接出错 |

## 第四章 RocketMQ（重头戏二，含与 Kafka 的正面对比）

### 4.0 消息队列是什么

**水库＋代办清单**。发送方把"要做的事"写成一条消息扔进队列就返回
（不等处理完），处理方按自己的节奏从队列里取出来干。
核心价值：**把"瞬间洪峰"切成"匀速细流"（削峰填谷）**，以及**把两件异步的事解耦**
（支付和发货不必手拉手同时完成）。

### 4.1 项目里的三个主题（一条消息 = 一个要办的任务）

| 主题 | 谁发的 | 谁消费的 | 干什么 |
|---|---|---|---|
| ORDER_CREATED | 抢购成功的瞬间 | 订单消费者 | 把订单写进数据库（洪峰变匀速） |
| DELIVER_GOODS | 支付回调成功后 | 发货消费者 | 道具进背包、订单变已发货 |
| ORDER_CLOSE_DELAY | 订单创建时 | 关单消费者 | **延迟 20 分钟才投递**——到点发现没付款就关单回补库存 |

### 4.2 关键机制

- **不丢消息三道保险**：发送方等仓库确认（同步发送）；消息在仓库落盘；处理方
  "干完才签收"，没签收的会被重新投递。
- **重复投递怎么办**：一定会发生，所以消费方必须幂等——订单表订单号唯一索引、
  发货流水唯一索引，重复消息第二次插不进数据库直接忽略。
- **延迟消息**：开源版只有 18 个固定档位（1 秒…10 分/20 分/30 分/1 时/2 时），
  没有 15 分钟档——所以业务从"15 分钟关单"调整为"20 分钟"（PRD 已修订）。
  这就是"标准组件的能力边界决定业务参数"的真实案例。
- **afterCommit 模式**（全项目用三次）：消息必须在数据库事务**成功提交后**才发出
  ——否则"消息发了、事务回滚了"就会产生幽灵消息。发送失败不回滚（数据已安全），
  缺口由对账重投兜底。这套组合的学名叫**事务性发件箱（Transactional Outbox）思想
  的朴素实现**。

### 4.3 RocketMQ vs Kafka（正面回答你的例子）

| 对比项 | RocketMQ（我们用的） | Kafka |
|---|---|---|
| 出身与定位 | 阿里为**电商交易链路**而生：订单、支付、库存这类"业务消息" | LinkedIn 为**日志与数据流**而生：日志收集、大数据管道 |
| 延迟消息 | **原生支持**（18 个固定档位，我们的 20 分钟关单直接用它） | 原生不支持，要自己造（另存一份+定时扫） |
| 事务消息 | 原生支持（半消息机制） | 无原生事务消息 |
| 吞吐量 | 十万级/秒，业务足够 | 百万级/秒（大数据场景的王者） |
| 消息堆积 | 支持（业务高峰堆积是常态） | 极强（本来就是堆日志的） |
| 中文生态/文档 | 国内电商广泛使用，资料多 | 国际社区为主 |
| 我们的业务要不要它 | 要：交易链路+延迟关单+削峰，全是它的主场 | 它的主场我们没进（不做日志管道和大数据） |

**各自适合什么场景（面试标准答法）**：
- **选 Kafka**：日志收集、用户行为埋点流、大数据分析管道——追求极致吞吐、
  不需要延迟消息和事务消息的场景；
- **选 RocketMQ**：电商交易链路（订单/支付/库存）、需要延迟消息、事务消息、
  业务消息堆积的场景——**我们的"限时抢购+延迟关单"恰好每一项都踩在它的主场**。
- 一句话总结：**不是谁更强，是主场不同**。我们的业务在 RocketMQ 的主场。

## 第五章 对账与定时任务（深夜巡逻队）

**为什么需要对账**：前面的每一环都保证了"几乎不会错"，但分布式系统里"几乎"不够
——消息可能丢、Redis 重启可能漂移、任何 bug 都可能造成"钱和货对不上"。对账是
**最后一张网**：每天凌晨把全系统的账核对一遍。

**三项核对**：①Redis 库存 vs 数据库推导值（上架总量+流水合计）——不一致按数据库
修复；②付了钱却没发货的订单——重投发货消息；③发了货却没付钱的异常——只登记
不自动修（拿不准的留给人工）。

**两个配套**：差异表用唯一索引保证"同一差异只登记一次"；定时任务抢分布式锁保证
双实例不重复扫。

**为什么流水表"只增不改"**：对账的前提是账本可信。如果流水可以被改，
"对账"就失去了事实基础。钱包流水/库存流水/抽卡记录/发货记录/通知日志，
五张账本全部只允许插入。

## 第六章 看见系统的四扇窗（可观测性）

掌控感来源：程序不再是黑箱，任何请求的"一生"都看得见。

| 窗户 | 是什么 | 什么时候用 |
|---|---|---|
| 日志（含 SQL 掐表插件） | 程序的自言自语；慢 SQL 自动打 WARN | 日常排查、压测定位慢查询 |
| Zipkin 行程单 | 每个请求经过哪些站、每站几毫秒 | "这个接口怎么慢了"——一眼看到卡在哪站 |
| Prometheus + Grafana | 每秒采集指标画成实时曲线 | 压测时看请求量、耗时、错误率曲线 |
| 健康体检（Actuator） | 数据库/Redis 等器官状态 | 启动后先看一眼全绿 |

四扇窗都是真实参与过破案的：事故 004（Zipkin 确认追踪断流）、事故 007（Redis 数据
考古）、循环 9（30 万成员下的毫秒查询）。

## 第七章 测试与工具链

- **自动化测试（36+ 条）**：把"验证步骤"写成代码，一条命令全量重跑。它防的不是
  "今天写错"，而是**"明天改别处时悄悄改坏了这里"**（回归保险）。人工验证是一次性的，
  自动化测试是永久的。
- **并发正确性测试**：30 线程抢 10 件、同一订单连关两次——超卖和重复回补靠"机器
  数数"验证，不靠肉眼。
- **MyBatis 插件机制**：MyBatis 允许在 SQL 执行流水线的工位上设卡（官方叫拦截器，
  俗称插件）。我们造了两张卡：9B 卡在"执行层"掐表（慢 SQL 告警），9C 卡在
  "对象层"做敏感字段加解密（身份证落库自动加密）。**同一机制、两个工位、两种用途**
  ——面试聊插件机制时这是你的立体答案。
- **Docker**：把 MySQL、Redis 等软件各装进一个"集装箱"（隔离的小环境）运行，
  一份配置文件（docker-compose）一键起全家。对比传统"每台机器手工安装"：
  环境一致、随删随建、端口冲突一目了然。
- **Linux/Shell**：全部验收脚本是 bash 写的（数据库检查、进程管理、curl 接口测试）
  ——这是"会用 Linux 命令行"的真实证据。

## 第八章 三条完整旅程（把所有零件串成电影）

### 旅程一：抢购的那一秒

```
玩家点击购买（带 JWT 手环）
→ 门口保安验手环 → 时间窗校验（没开售？拒绝）
→ Redis 执行 Lua 脚本：一人一单？库存够吗？→ 扣！
   （失败者在此被拒：数据库毫发无伤——98% 的人止步于此）
→ 赢家只做一件事：发 ORDER_CREATED 消息，立刻收到订单号
→ （事务提交后）埋下 20 分钟延迟关单的"定时炸弹"
→ 订单消费者收到消息 → 写订单表（带限购唯一索引）→ 记销售流水
```

### 旅程二：付款的三分钟

```
玩家在假支付公司页面点"确认付款"
→ 支付公司按当前"作恶开关"发回调（可能延迟/重发3次）
→ 商户验 HMAC 签名（假通知死在这）→ 通知号记账（重复通知死在这）
→ 状态机：待支付→已支付（重复回调死在这）
→ 同一事务：扣钻石、记钱包流水、（提交后）发发货消息＋排行榜计分
→ 发货消费者：发货流水（防重）→ 背包入道具 → 订单变已发货
→ 排行榜实时 +N 分（30 万成员中 4.7 毫秒找到你的位置）
```

### 旅程三：深夜的自动巡逻

```
20 分钟没付款的订单：延迟消息到点 → 状态机守卫 → 关单 → 库存回补 → 限购释放
（消息丢了？）→ 每 60 秒扫表兜底（双实例抢分布式锁，只有一个干活）
凌晨 2 点：对账开工 → 库存漂移按数据库修复 → 发货缺口重投 → 异常登记留人工
```

## 第九章 已知边界与诚实声明（面试加分区）

1. **不拆微服务**：单机项目拆八个服务是"为了用而用"；我们只拆了假支付公司
   （它模拟"外部公司"，天然独立）。面试答法："模块边界=未来的服务边界，拆分
   要跟着信任边界走，不跟着简历关键词走"。
2. **不用限流中间件（Sentinel 等）**：抢购的正解是"门口快速拒绝+削峰"，引限流
   反而挡真人玩家。滑动窗口限流在循环 10 以"自研 30 行"形式补在回调入口上。
3. **加密字段无法模糊查询**：实名信息不需要模糊查；需要等值检索的方案是另建
   HMAC 确定性索引列（代价能讲清）。
4. **ZSET 深翻页会慢**：业务只查前 100 和我的排名，不越界。
5. **开源 RocketMQ 延迟档位固定**：无 15 分钟档，业务调整为 20 分钟。
