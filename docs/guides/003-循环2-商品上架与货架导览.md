# 导览 003：循环 2 —— 商品上架与货架是怎么工作的（新手版）

> 延续 002 的讲法：比喻贯穿，术语全部配人话。

## 这一循环做了什么

运营（管理后台）现在可以**上架商品**了；玩家登录后能看到**货架**——每件商品挂着
状态牌（即将开售/抢购中/已售罄/已结束）和倒计时。中间还多了两个重要角色：
**门口的大黑板（缓存）** 和一套自动生成的**接口说明书网页**。

## 五个关键角色

### 1. 道具字典 + 贩售商品：登记簿和摊位

- `item` 表 = **商品登记簿**：道具叫什么、稀有度、描述、图片。以后抽卡的"卡"也登记在这本簿上；
- `goods` 表 = **摊位**：从登记簿里挑一件道具摆出来卖——标价（钻石）、划线原价（游戏味的"原价199现价99"）、库存几件、几点开卖几点收摊。

### 2. 状态牌是"算出来的"，不是"写死的"

摊位上从不存"我现在是什么状态"，每次有人问，就用**当前时间 + 实时库存**现算：

```
现在 < 开售时间        → 即将开售（挂倒计时：还有多久开卖）
开售中 且 库存 > 0      → 抢购中（挂倒计时：还有多久收摊）
开售中 但库存 = 0       → 已售罄
现在 > 结束时间         → 已结束
```

为什么不算好存起来？——存下来的状态会撒谎（库里写着"抢购中"，实际库存早清零了），
现算的永远不会。

### 3. 门口的大黑板（Redis 缓存）——本循环的技术主角

**问题**：开售前一小时几十万人反复刷货架，如果每次都去数据库（大仓库）翻一遍，
仓库门口会被挤爆。而大家看的是**同一块货架**——完全可以让所有人看同一块黑板。

**方案**：货架内容抄成一份 JSON 文本放在 Redis（门口黑板），5~7 分钟内所有人看黑板；
黑板上没有才进仓库，出来顺手抄一份上新黑板。

黑板还有三条讲究（面试三大故障的活体对应）：

- **同一秒全擦 = 雪崩**：如果所有黑板内容都恰好 5 分钟过期，到期那一刻几十万请求
  同时冲进仓库。对策：**过期时间随机**（5~7 分钟不等），让过期时间错开；
- **恶意问不存在的货架 = 穿透**：有人故意狂刷接口让每次都进仓库。对策：**空结果也
  上黑板**（缓存 60 秒的空货架），狂刷的人只能看到空黑板；
- **改价了黑板还是旧价 = 一致性问题**：运营改价后，必须让黑板作废。这就是下一位角色。

### 4. 延迟双删（改价时擦两次黑板）

运营改价的完整动作：**擦黑板 → 进仓库改价 → 隔 0.5 秒再擦一次黑板**。

为什么要擦第二次？第一次擦完到仓库改完价的间隙里，可能正好有个请求刚从仓库抄了
**旧价**、正准备往黑板上写——它写的这份"脏黑板"只有第二次延迟擦才能清掉。
这不是理论洁癖，是我们缓存测试里真实验证的行为。

### 5. 管理端保安（第二套身份体系）

玩家走 JWT 手环，运营走另一套：登录用管理密码（配置文件里，默认 `admin123`），
换来一个**固定暗号**（`X-Admin-Token`），以后每个管理请求都带暗号，保安只认暗号。
两套身份互不相通——玩家的手环开不了运营的门，反之亦然。

## 接口说明书网页（springdoc）

浏览器打开 **http://localhost:8080/swagger-ui/index.html**——项目所有接口自动列成
一张可点击的表，每个接口能直接在网页上填参数试跑。以后再也不用手拼 curl。

## 亲眼看（建议顺序）

程序跑起来后，先开 http://localhost:8080/swagger-ui/index.html 对照着玩，或用 curl：

```bash
# 1. 运营登录拿暗号
curl -X POST http://localhost:8080/api/admin/login -H "Content-Type: application/json" -d '{"password":"admin123"}'

# 2. 上架一件商品（时间用 ISO 格式；把开售时间改成几分钟后来亲眼看到计时变化）
curl -X POST http://localhost:8080/api/admin/goods -H "Content-Type: application/json" -H "X-Admin-Token: lootrush-admin-token-2026" -d '{"name":"星陨战刃","description":"限时贩售的传说武器","price":50,"originalPrice":100,"stock":5000,"saleStartTime":"2026-10-26T21:00:00","saleEndTime":"2026-10-26T22:00:00"}'

# 3. 玩家登录拿手环（没账号先注册，参考导览002）
curl -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" -d '{"username":"player1","password":"pass123"}'

# 4. 看货架：应看到星陨战刃 + 状态 + 倒计时 + 剩余 5000
curl http://localhost:8080/api/goods/list -H "Authorization: Bearer <玩家token>"

# 5. 运营改价
curl -X PUT http://localhost:8080/api/admin/goods/1/price -H "Content-Type: application/json" -H "X-Admin-Token: lootrush-admin-token-2026" -d '{"price":30}'
# 再看一次货架 → 新价 30（延迟双删已把旧价黑板擦掉）
```

三个对照窗口：

- **DBeaver**：lootrush 库多了 `item` 和 `goods` 两张表，能看到刚上架那行；
- **Redis 实况**：Git Bash 敲 `docker exec -it mall-redis redis-cli` 后输
  `GET goods:list`（看到整架 JSON）和 `GET stock:1`（看到 5000）——黑板和库存牌亲眼看；
- **Zipkin**：刷几次货架，行程单里能看到每次请求的耗时；连续刷两次，
  第二次的耗时明显更短（黑板命中，没进仓库）。

## 本循环踩到的小坑

SQL 手写时把 `i.image_url` 写成了 `i.imageUrl`——数据库列名是下划线风格
（image_url），Java 字段是驼峰风格（imageUrl），**在 SELECT 里给列起驼峰别名时
漏了一列**。报错长这样：`Unknown column 'i.imageUrl'`。
以后看到 "Unknown column"，就是"SQL 里的列名和表里的列名对不上"，去对表结构即可。
