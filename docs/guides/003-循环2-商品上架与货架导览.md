# 导览 003：循环 2 —— 商品上架与货架查询

> 讲法约定：先用一个比喻帮你建立直觉，随后立刻给出规范的技术表述。
> 面试时请使用规范表述；比喻只是入门的脚手架。

## 这一循环做了什么

运营（管理后台）可以上架商品、修改价格；玩家登录后查询货架，看到每件商品的
状态（UPCOMING / ON_SALE / SOLD_OUT / ENDED）和倒计时。玩家侧查询走 Redis 缓存，
并落地了缓存一致性的标准做法。接口文档网页（springdoc）也在本循环接入。

## 一、数据模型：item 表与 goods 表

比喻：item 是"登记簿"，goods 是"摊位"。
规范表述：`item` 是**道具字典**（道具名、稀有度、描述、图片，抽卡循环会复用）；
`goods` 是**贩售配置**（关联的道具、售价、划线原价、总库存、开售/结束时间）。
一件道具可以有多次不同的贩售配置，所以拆成两张表而不是一张。

## 二、商品四态：推导而非存储

状态不作为字段落库。每次查询用「当前时间 + 实时库存」推导：

```
now < sale_start            → UPCOMING（倒计时 = 距开售的秒数）
sale_start ≤ now ≤ sale_end 且库存 > 0 → ON_SALE（倒计时 = 距结束的秒数）
sale_start ≤ now ≤ sale_end 且库存 = 0 → SOLD_OUT
now > sale_end              → ENDED
```

理由：存储的状态会和事实脱节（库里写着"抢购中"而库存早已清零），
推导的状态永远与当前事实一致。这是个"**derived data（派生数据）不落库**"的通用原则。

## 三、Redis 缓存（本循环技术主角）

比喻：货架内容抄在"门口的大黑板"上，大家看黑板，黑板上没有才进仓库。
规范表述：这是 **Cache-Aside（旁路缓存）模式**——
读请求先查 Redis 键 `goods:list`（整架货架序列化成一条 JSON 字符串）；
命中（hit）直接返回；未命中（miss）则回源（query MySQL），结果**回填**（回写）到
Redis 并设置过期时间 TTL。数据库压力与读并发解耦，这就是"读多写少场景上缓存"的含义。

缓存 TTL 的设置与三个经典故障的对应（均已落地）：

| 故障 | 含义 | 本项目的对策 |
|---|---|---|
| 缓存雪崩 | 大量键同一时刻集中过期，请求洪峰直接砸穿到数据库 | TTL 随机化：货架缓存 5~7 分钟随机取值，过期时间被刻意错开 |
| 缓存穿透 | 恶意查询根本不存在的数据，缓存永远无法命中，每次都打数据库 | 空结果也缓存（空货架缓存 60 秒），攻击请求只能拿到空缓存 |
| 缓存击穿 | 单个热点键过期瞬间，大量并发同时回源 | 随机 TTL 已缓解；"逻辑过期/热点永不过期"留到压测循环按需加固 |

（第三个表格行如实标注了现状——面试时能讲清"已做什么、还欠什么"比假装全做了更加分。）

## 四、改价与延迟双删

比喻：改价时"擦两次黑板"，中间隔半秒。
规范表述：**延迟双删**。流程：

```
1. 删除缓存（第一删）        —— 让新请求无法再读到旧缓存
2. 更新数据库
3. 异步延迟 500ms 再删一次    —— 清掉"第一删之后、库更新完成之前"
                                 并发读把旧值回填进缓存的脏数据
```

为什么必须删第二次：第 1 步和第 2 步之间存在窗口，此时进来的读请求会发现缓存
未命中、去数据库读到的**还是旧值**（库尚未更新完），并把它回填进缓存——
这份脏缓存没有第二次删除就会一直服务到自然过期。
本循环的自动化测试 `price_update_triggers_delayed_double_delete` 验证的就是这个行为。

另一个面试常见追问：为什么是"删缓存"而不是"改缓存"？
答：改缓存有并发写乱序问题（A 先改库后改缓存、B 后改库先改缓存，缓存停在 A 的值）；
删除是幂等操作，语义上只是"声明作废"，更安全。

## 五、管理端鉴权：X-Admin-Token

规范表述：管理端与玩家端是**两套独立身份体系**。玩家走 JWT（Bearer Token，
JwtInterceptor 校验）；运营走**静态 Token**——登录校验管理密码后下发
`X-Admin-Token`（配置文件中的固定值），AdminInterceptor 对 `/api/admin/**`
（登录接口除外）逐一校验。玩家 Token 打不开管理接口，反之亦然。

## 六、接口文档（springdoc）

程序运行时打开 **http://localhost:8080/swagger-ui/index.html**：
项目全部接口自动列出（路径、参数、返回结构），可在网页上直接填参数调用。
原理：springdoc 扫描代码里的 Controller 注解，实时生成 OpenAPI 描述文档。

## 亲眼看（建议顺序）

程序跑起来后（可直接用 swagger-ui 网页操作，下面给 curl 版）：

```bash
# 1. 运营登录，拿 X-Admin-Token
curl -X POST http://localhost:8080/api/admin/login -H "Content-Type: application/json" -d '{"password":"admin123"}'

# 2. 上架（开售时间设成几分钟后，稍后能亲眼看到状态翻转）
curl -X POST http://localhost:8080/api/admin/goods -H "Content-Type: application/json" -H "X-Admin-Token: lootrush-admin-token-2026" -d '{"name":"星陨战刃","description":"限时贩售的传说武器","price":50,"originalPrice":100,"stock":5000,"saleStartTime":"2026-10-26T21:00:00","saleEndTime":"2026-10-26T22:00:00"}'

# 3. 玩家登录拿 JWT（没账号先注册，见导览002）
curl -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" -d '{"username":"player1","password":"pass123"}'

# 4. 查货架：应看到星陨战刃 + 状态 + 倒计时 + stockLeft=5000
curl http://localhost:8080/api/goods/list -H "Authorization: Bearer <玩家token>"

# 5. 改价 → 再查货架，价格已是新值（延迟双删已把旧缓存清掉）
curl -X PUT http://localhost:8080/api/admin/goods/1/price -H "Content-Type: application/json" -H "X-Admin-Token: lootrush-admin-token-2026" -d '{"price":30}'
```

三个对照窗口（每个循环验收的标准三件套）：

- **DBeaver**：lootrush 库的 `item`、`goods` 表能看到上架的数据。
  数据变了不自动刷新——**数据页按 F5** 重新查；**新表**要左侧树右键 Tables → Refresh；
- **Redis**：`docker exec -it mall-redis redis-cli` 后：
  `GET goods:list`（整架 JSON 缓存）、`GET stock:1`（预热的库存数 5000）；
- **Zipkin**：连刷两次货架，第二次行程单耗时明显更短（缓存命中，没回源）。

## 本循环踩到的小坑

手写 SELECT 时把列 `i.image_url` 误写成 `i.imageUrl`，报错
`Unknown column 'i.imageUrl' in 'field list'`。
背景：MySQL 列名用下划线风格（image_url），Java 字段用驼峰（imageUrl），
转换发生在两处——MyBatis 的 map-underscore-to-camel-case 配置（自动）和
手写 SELECT 里显式的 `AS imageUrl` 别名（手动，漏写就报这个错）。
排错口诀：看到 Unknown column，就拿 SQL 去对表结构（DESC 表名），列名逐个核对。
