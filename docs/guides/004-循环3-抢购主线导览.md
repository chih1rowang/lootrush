# 导览 004：循环 3 —— 抢购主线（Lua 原子扣减 + 削峰建单）

> 讲法同前：比喻搭脚手架，紧跟规范表述。这是全项目的心脏循环。

## 这一循环做了什么

玩家可以抢购了：点一次"购买"，系统在 Redis 里**一口气**完成"查他买过没有＋查库存＋扣库存"，
抢到的立刻拿到订单号；订单的数据库写入由消息队列的消费者**慢慢匀速**完成。
超卖为零、一人一单、数据库在洪峰下零直接压力——三条铁律同时成立。

## 四个关键角色

### 1. Lua 脚本：不可插队的柜台窗口

比喻：柜台前立一块"办理中请排队"的牌子，业务员办完一件事才叫下一个号。
规范表述：Redis 采用**单线程执行命令**，一段 Lua 脚本提交后整体执行完毕才会轮到其他
命令——**原子性由此而来**。脚本 deduct_stock.lua 一次网络往返完成三件事：
检查判重标记（一人一单）→ 读库存 → 库存充足则扣减并写判重标记。
返回码：0 成功 / -1 售罄 / -2 库存未预热 / -3 已抢购过。

为什么不用"先 GET 再 DECR"两步：两步之间可能插进别人的命令，两个请求都读到
"还剩 1"然后都扣减——这就是超卖。本循环的并发测试用 30 线程抢 10 件库存，
成功数恰好 10、终态库存 0，超卖为 0 是被机器验证过的事实。

### 2. 门口快速拒绝

规范表述：抢购注定多数人失败（10000 人抢 5000 件），失败者的请求必须在 Redis 层
就被拒绝（售罄/已抢过/未开售），**绝不允许触达数据库**。数据库连接是稀缺资源，
留给真正的赢家。

### 3. RocketMQ：水库（削峰填谷）

比喻：洪水（瞬时 5000 个赢家同时要建订单）先灌进水库，下游按自己的节奏放水灌溉。
规范表述：抢购成功路径只做"扣减 + 发一条 ORDER_CREATED 消息"即返回；
**订单落库由消费者异步完成**。数据库写入从"瞬时洪峰"变为"匀速水流"——
这就是削峰填谷（traffic shaping）。消息不丢：syncSend 同步等待 broker 确认，
发送失败则立刻回补 Redis 库存并撤销判重标记（补偿逻辑）。

### 4. 消费者：匀速写入端 + 两道保险

OrderCreatedListener 消费消息并插入 order_info 表，带着两个防御：

- **消费幂等**：消息可能被重复投递（网络重试等）。order_no 上有唯一索引，
  第二次插入触发 DuplicateKey（uk_order_no）→ 识别后直接忽略。同一消息来多少次，
  订单都只有一条；
- **数据库铁闸 + 补偿**：极端情况下（如判重标记恰好过期）同一人同一商品的第二单
  越过 Redis 淜到消费者，(user_id, goods_id, active_flag) 唯一索引拦下
  （uk_user_goods_active）→ 补偿：Redis 库存 +1、删判重标记。
  **Redis 是快速的第一道门，数据库唯一索引是永不失效的最后一道闸。**

### 附：限购的 NULL 技巧（表设计回顾）

order_info 的 active_flag：订单活跃时 = 1，关单时置 NULL。
MySQL 唯一索引**不约束 NULL**，于是 (user, goods, 1) 唯一 = 活跃期一人一单；
关单置 NULL 后 = 同一索引放行再抢。一条索引同时实现"锁死"与"放行"。

## 一次抢购的完整旅程

```
玩家 POST /api/purchase/{goodsId}（带 JWT）
→ 保安验手环放行，带入 userId
→ 时间窗校验（未开售/已结束 → 门口拒绝）
→ Redis 执行 Lua（判重+查+扣，一次往返）
   ├─ -3 已抢过 / -1 售罄 → 立刻返回失败（数据库毫发无伤）
   └─ 0 成功 → 生成订单号 → syncSend ORDER_CREATED → 返回订单号
                                   ↓（异步）
              消费者收到 → 插入 order_info（status=0 待支付）
                ├─ uk_order_no 冲突 → 幂等忽略
                └─ uk_user_goods_active 冲突 → 补偿 Redis
```

前提：IDEA 里 **Build → Rebuild Project** 后运行（老规矩：我在命令行编译过）。
用你循环 2 上架的商品（或先跑导览003再上架一件库存 5、正在售卖的商品）。

```bash
# 登录拿手环（player1 若没注册先 POST /api/auth/register）
TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" -d '{"username":"player1","password":"pass123"}' | grep -oE '"token":"[^"]+"' | cut -d'"' -f4)
GOODS_ID=16   # ← 换成你要抢的商品ID（查货架 /api/goods/list 里看）

# 0. 抢之前：看 Redis 库存牌
docker exec mall-redis redis-cli GET stock:$GOODS_ID

# 1. 抢购！应返回 orderNo
curl -s -X POST http://localhost:8080/api/purchase/$GOODS_ID -H "Authorization: Bearer $TOKEN"; echo

# 2. 等两秒再看库存牌：应减 1
docker exec mall-redis redis-cli GET stock:$GOODS_ID

# 3. 再抢一次：应被拒"每人限购一份"（一人一单）
curl -s -X POST http://localhost:8080/api/purchase/$GOODS_ID -H "Authorization: Bearer $TOKEN"; echo

# 4. 我的订单：应看到刚那张 status=0 的订单（消费者异步落库，最多等几秒）
curl -s http://localhost:8080/api/order/my -H "Authorization: Bearer $TOKEN"; echo

# 5. 实况转播：看判重标记（TTL 内存在）
docker exec mall-redis redis-cli KEYS 'buyflag:*'
```

三个对照窗口：

- **RocketMQ 控制台** http://localhost:8180 ：Topic 里出现 ORDER_CREATED，
  消息数随抢购增长；Consumer 里能看到 lootrush-order-group；
- **DBeaver**：order_info 表出现订单行（F5），active_flag=1，status=0；
- **Zipkin**：抢购请求的行程单，能看到 Redis 和 MQ 发送两站的耗时。

## 本循环踩到的小坑（两个）

**坑1：订单号塞进 Long 溢出。** active_flag 曾设计存"订单号转数字"，但订单号 20+ 位，
Long 上限 19 位，消费者里 Long.parseLong 当场 NumberFormatException，消息无限重试。
教训：数值字段的取值范围是设计约束，超长标识符应存 VARCHAR 或改用短数值标记
（最终方案：active_flag=1 常量，语义由唯一索引承担）。

**坑2：测试依赖"数据库是干净的"。** 商品测试用 get(0) 取"最新商品"，被手工验证
留下的旧数据搅了排序。教训：测试定位数据要按唯一 ID 过滤，不要按列表位置；
自动化测试必须容忍数据库里有历史数据。
