# 事故报告 №008：对账上线日三连败——Long 装箱双杀与事务快照陷阱

- 日期：2026-10-27
- 严重程度：中（循环7测试三处失败，定位耗时约30分钟；其中装箱问题具备潜伏性）
- 状态：已修复

## 1. 现象

循环7 测试首次全量运行，29 条中 3 处失败：
① 库存对账测试"第二轮不应再发现本差异 expected:0 but was:3"；
② 发货缺口测试重投消息 10 秒后仍查不到发货记录（但事后查库，记录其实在）；
③ 商品缓存测试 NoSuchElementException（该测试连续多日全绿，当日突然开始失败）。

## 2. 复现步骤

①② 跑 ReconServiceTest 即现；③ 在商品 ID 总量超过 127 后跑 GoodsServiceTest 即现。

## 3. 排查过程

①②③ 各自取证：
- ① 怀疑 Redis 被外部改动 → 查 8080 扫表任务无嫌疑 → 重看比较逻辑，发现
  `Long actualVal != Long expected` 是**对象引用比较**：库存 ≤127 时命中 Long 装箱缓存
  碰巧成立，超过 127（如库存5000）永远"不相等" → 每轮误报漂移；
- ② 查库发现发货记录其实已存在（消费者已完成）→ 测试却轮询不到 →
  MySQL REPEATABLE READ：@Transactional 测试事务活在**首查快照**里，
  消费者在快照之后提交的行永远不可见（PurchaseFlowTest/DeliverGoodsTest 无事务注解
  所以从未踩中——对照即答案）；
- ③ 报错行是 `v.id() == id`——**同款装箱引用比较**！商品ID一直 <128 时靠装箱缓存
  碰巧为真；用户验收脚本大量造商品后 ID 越过 127，测试从那一刻起注定失败。
  Zipkin 佐证排除外因（近期无任何货架请求改写缓存）。

## 4. 根因

三个失败，两个根因：
- **Long 装箱比较**（两处：生产代码 ReconService、测试代码 GoodsServiceTest）——
  数值当对象比，靠 -128~127 缓存区侥幸存活，数据量增长越过缓存线后必然爆发；
- **事务快照与异步写入的隔离鸿沟**——需要观察"另一事务提交结果"的测试不能自己开事务。

## 5. 修复

① 改为 `actualVal.longValue() != expected.longValue()` 数值比较；
③ 两处 `==` 改 `.equals()`；
② ReconServiceTest 去掉 @Transactional，改手动清理（对齐既有模式），并在类注释写明原因；
顺带：给 deliver-gap 测试补上"不断言订单状态"的注释（消费者线程看不到测试未提交行）。

## 6. 预防

- **数值比较永远用 == 前先自问：是 long 还是 Long？** 代码评审检查项；
- 测试要观察异步提交结果时禁用 @Transactional（项目内已有两种模式的先例对照）；
- 本案最大教训：**"一直绿"的测试不等于"正确"的测试——它可能只是数据还没长到引爆点**。
  商品 ID 越过 127 的那一刻，潜伏的装箱 bug 准时起爆。

## 补记（2026-10-27 验收期）：我的补录造出了幻影账

验收重测时发现商品 96 的推导值从 6 变 5——追查发现一条 **RECONGAP1 的 SALE 流水**。
RECONGAP1 是验收脚本直接插库的合成缺口订单，从未真实扣过库存，不应有销售账。
根因是我此前的 SALE 补录 SQL 只判断"PURCHASE 订单缺 SALE 就补"，
**分不清"真订单丢了账"和"合成订单本就不该有账"**，把假单也补了账；
后续对账基于错账推导，把 Redis 从正确的 6 改成了错误的 5。

修复：删除幻影 SALE；合成订单已从源头治理（缺口订单号统一 RECONGAP% 前缀，
补录工具 docs/sql/backfill-stock-flow.sql 永久排除该前缀 + 仅认 P% 订单）。

教训：**补账前先问"这笔账缺了，是因为丢了，还是因为本来就不该有"** ——
对账工具修复数据时，它自己的 WHERE 条件也需要一次"对账"。
