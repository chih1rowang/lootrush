# 事故报告 №006：测试被自己昨天的残留数据毒倒（缺失 @Transactional）

- 日期：2026-10-26
- 严重程度：中（测试集体假失败，掩盖路径具迷惑性）
- 状态：已修复

## 1. 现象

循环 5 开发中运行全量测试：PayCallbackTest 5 条中 4 条失败，
失败模式蹊跷——回调接口返回 code=0（成功），但订单状态没变、钻石没扣。

## 2. 复现步骤

第一跑（数据干净）全绿 → 不清理数据库 → 第二跑必现。

## 3. 排查过程

1. 失败断言显示"code=0 但数据未动"→ 推断回调走了某条'返回成功但不做事'的捷径；
2. PayService 里唯一的此类捷径：DUP_NOTIFY（通知号唯一索引冲突 → 幂等忽略）；
3. 查 pay_notify_log 表：果然躺着昨天测试插入的 N1/SAME/A1/A2/N9/EVIL——
   用户验收循环 4 时的输出 5.3 里就有 `N1 PT179301805684038`，尸证当时就在眼前；
4. 根因确认：PayCallbackTest 没有加 @Transactional，昨天首跑的数据永久提交入库，
   今天第二跑插入相同通知号 → 唯一索引冲突 → 全部走幂等忽略捷径。

## 4. 根因

集成测试未回滚数据（缺 @Transactional），且使用了固定值唯一键（通知号）。
数据库是有记忆的：首跑即污染环境，从第二跑起测试对着自己昨天的尸体验尸。

## 5. 修复

1. PayCallbackTest 加 @Transactional（每个测试方法结束自动回滚）；
2. 物理清除库中的残留毒数据（pay_notify_log 固定通知号行、payuser% 用户）；
3. 顺手修复 BagMapper 的同款老错误（i.imageUrl → i.image_url AS imageUrl，
   循环 2 已犯过一次，本次第二次）。

## 6. 预防

- 新建集成测试类的固定动作：@SpringBootTest 下面必须跟 @Transactional（除非测试
  有明确理由不能回滚，如多线程/异步落库验证——那类测试用带时间戳的唯一数据）；
- "昨天是绿的"不构成今天的信任：环境（数据库/Redis）是有状态的，
  首跑全绿只证明首跑那一次；
- 检查项固化：每写一个 SELECT 逐列对照表结构（下划线/驼峰）。
